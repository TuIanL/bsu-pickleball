### 5.4 双摄覆盖的正确算法（v1 错误，已改正）

v1 用 `154 ÷ 427 = 36%` 得出"双摄覆盖约 36%"，**这是错的**：分子是轨道数、分母是 take 数，量纲不同。

正确做法（本次实测）：

```sql
-- 每个 take 的轨道数分布
SELECT n AS tracks_in_take, count(*) AS takes
FROM (SELECT capture_take_id, count(*) n FROM capture_tracks GROUP BY capture_take_id)
GROUP BY n;
-- 结果：1 条轨道 → 154 个 take（没有任何 take 有 2 条）

-- dual take 的轨道数
SELECT t.id, t.capture_mode,
       (SELECT count(*) FROM capture_tracks k WHERE k.capture_take_id=t.id) AS tracks
FROM capture_takes t WHERE t.capture_mode='dual';
-- 结果：8 个 dual take，tracks 全部为 0

-- 有轨道的 take 按模式分布
SELECT t.capture_mode, count(DISTINCT t.id)
FROM capture_takes t JOIN capture_tracks k ON k.capture_take_id=t.id
GROUP BY t.capture_mode;
-- 结果：single 154，dual 0
```

**结论**：本库的双摄轨道覆盖率不是 36%，而是 **0**。8 个 dual take 均无任何轨道记录，154 条轨道全部挂在 single take 上且 `role` 单调为 `primary`，说明双摄记录链路从未在本库写入过 `secondary`。这比 v1 的判断严重得多，需要作为独立缺陷跟踪。

### 5.6 关于《匹克球视频采集与动作标注规范》（v2 改正）

**正确表述**：规范**已存在于项目资料中，但尚未确认纳入 GitHub 仓库与版本控制**。落地位置待用户指明，纳入仓库后应作为架构设计的一等输入。

同时，规范以**原始视频帧号**为权威时间基准，而当前双摄链路还涉及 PTS、`capture_takes` 时间轴与同步映射。第二轮必须明确区分并分别定义三个概念，不能只保留其中一个：

| 概念 | 语义 | 归属 |
|---|---|---|
| 原始视频帧号 | 单文件内可复算的物理基准 | 证据层（不可变） |
| 源视频时间戳（PTS） | 相机侧采集时刻 | 同步层（可校准、可侧车修正） |
| 统一采集时间轴（take 时间） | 跨机位对齐后的业务时间 | 分析层（可重建） |

这三者的换算关系与误差界，应作为《核心数据契约》的首要条目。
