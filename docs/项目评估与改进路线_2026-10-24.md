# 项目全面评价与改进路线

评估日期：2026-10-24。评估对象：匹克球分析项目“瞬境”。

## 评估范围与证据

本机代码为 `2665bc3` 加上尚未提交的 Windows 适配。只读核查发现，线上 main 已到 `04877ef`，领先本机 17 个提交。本次阅读了线上新增模块架构、执行器、三个模型适配器、验收记录和 CI 配置，没有更新或覆盖本机源码，也没有把线上文档中的运行记录当作在本机重新执行的结果。

线上最新 quality、backend-lint、openspec 三项检查均为 success，见 [CI 记录](https://github.com/TuIanL/bsu-pickleball/actions/runs/39903382693)。部分真实素材测试被显式跳过，CI 还排除了两个依赖特殊素材/环境的文件；通过代表该检查范围通过，不等同于全功能现场验收。

以下评分是评审者对成熟度和证据充分性的主观判断，不是模型准确率、用户满意度或市场估值。

## 总体结论

项目具备继续投入的基础，当前最合适的定位是“面向固定场地训练复盘的研究型产品原型”。整体成熟度约 6/10：工程实现与系统整合较强，真实数据验证、普通用户易用性和已证明的科研创新仍需补足。

作为学生项目，真实模型、采集、同步、任务执行和证据管理的实现广度是明确优点。作为教练日常工具，还需要证明能稳定节省复盘时间。作为科研成果，需要把某一个问题做成可复现、可对比、可量化的贡献。

| 维度 | 主观评分 | 依据 |
| --- | --- | --- |
| 功能覆盖 | 7/10 | 上传、标定、人体/姿态、球分析、双摄、时间线和报告已有实现 |
| 工程与迭代基础 | 7/10 | 独立 Worker、持久化、失败证据、鉴权、CI、模块缓存均有实际代码 |
| 普通用户可用性 | 5/10 | 模型、驱动、标定、同步、身份确认和故障解释的使用成本仍高 |
| 算法结论的证据充分性 | 4/10 | 局部推理可运行，但身份、几何、动作和完整报告缺少统一外部验证 |
| 产品价值闭环 | 5/10 | 视频与分析关联已有基础，训练建议页仍用演示数据，持续使用证据不足 |
| 已证实的算法原创性 | 4/10 | 基础模型来自已有工作，专项方法尚缺系统消融与强基线对照 |
| 商业交付准备度 | 4/10 | 部署、支持成本、长期运行、访问管理和真实教练使用效果仍需试点证据 |

这些分数不表示算法只有四成准确，而表示当前资料不足以支持更强的准确性承诺。

## 可用性：开发者可以使用，普通用户尚需较多协助

优点是链路真实存在。本机此前完成了真实短片的人体、球、场线和 26 点姿态推理，并生成叠加视频。上传、分析任务与产物并非只有页面占位。Windows 启停与调试入口也已补齐。

主要成本发生在正式分析之前：视频机位是否合格、四角是否标对、两路时间是否对齐、四人身份是否确认，以及本机模型环境是否匹配。对开发者而言可诊断，对教练和普通球员而言仍可能成为阻碍。

本机任务 `job-b8f1a461c9` 虽然 completed，个人位置可视化仍为 `no_data`、球员轨迹状态为 `no_detections`。该任务只有 3 秒、未做正式测量校准，因此不能据此判定完整算法失败；它明确说明任务完成、产物存在、指标有效是不同层次。

建议把产品结果分为：已处理、存在有效证据、可支持某项指标、已通过质量检查。完成页面应说明哪些内容可用、哪些缺失、原因是什么、如何补救，不能只显示一个绿色完成状态。

首批用户建议聚焦固定机位的校队教练、课程教师或合作场馆。先做赛后复盘，验证“快速找到值得讲解的片段”这一具体价值，再扩大目标人群。

## 算法可信度：身份与几何是下游报告的基础

### 四人持续身份

活跃变更 `restore-confirmed-four-player-joint-analysis` 仍未勾选完整时段追踪、长缺口、末段与身份硬门槛的真实验收。代码对冻结名册、端位、关联竞争和质量审计做了很多处理，这是有价值的工作，但提交了修复不能替代修复有效的实测。

身份切换会把两个人的数据混合，继而影响个人热力图、移动距离、搭档间距和训练建议。应优先测量 IDF1/HOTA、身份交换数、每人有效覆盖率与最长缺口，而不是先增加报告图表。合法换边与身份污染必须区分，球员身份、队伍归属和所在场地端位不能混成同一个概念。

现有变更提出覆盖率 ≥0.70、最长缺失 ≤2 秒等门槛，适合先作为项目内部基线，尚不能直接定义商业可用性；不同指标对缺失和身份错误的容忍度不同。

### 标定、球与轨迹

需要分别验证脚点地面投影、球的二维检测、重建轨迹和真实落点。单应性描述地面平面关系，空中球的平面投影不能直接作为真实落点。重建曲线是否平滑也不能替代真值误差测量。

已有短片里，6 个采样帧有 2 帧检出球，产物有 6 个轨迹样本。这不是 33.3% 的球检测准确率，也不是 6 次直接观测：需要明确检测、预测、插值、重建各自的来源。建议每个展示点保留来源与置信度，低质量段不进入正式统计。

### 回合切分

本机模型包 `evaluation_report.json` 记录 1108 个测试样本：accuracy 0.9711、Macro-F1 0.9651；比赛类 precision 0.9840、recall 0.9194。混淆矩阵为 `[[308,27],[5,768]]`，即 335 个比赛类样本有 27 个被预测为非比赛。

这是值得肯定的已有结果。但它不能证明 1108 场比赛上的效果，也不能直接代表自动跳播会丢掉多少比赛时间，因为还存在采样、重叠窗口和时序解码。当前模型包汇总没有给出回合开始/结束边界误差与跨场地泛化结果。

训练配置已提出按 CaptureTake 分组、禁止跨集合片段重叠、留一场验证，方向正确。下一步应提供实际划分清单与逐场结果，补充边界 MAE、完整回合召回率、有效比赛被误跳过的时长和人工修正量。

### 姿态与训练结论

26 点骨架推理成功，证明模型能够运行。要评价挥拍类型、准备姿态或动作稳定性，还需定义可观察事件、人工标注和误差容忍度。目前 TrainingPage 的建议与进展曲线仍直接引用 demoData；应把演示内容与真实训练建议的能力边界写清楚。

## 工程：基础较好，架构升级值得保留

线上新版增加 `modular_v1`：按时间窗口展开依赖、独立请求能力、复用不可变产物、保留失败部分和血缘信息。这能缩短算法调试循环。已实际实现的是 `player.detect`、`ball.detect`、`pose.sequence`；21 个后续能力仍为 planned，普通产品请求继续使用 legacy。新模块中的姿态主体是逐帧 observation，尚未具备稳定跨帧身份，不能把架构升级当成跟踪算法已经升级。

新版记录了真实单/双摄 60–90 秒窗口验证。一个 30 秒窗口的三能力首次执行为 204.916 秒，全缓存单路为 10.313 秒、双路为 20.077 秒；该记录包含机器与初始化条件，不是本机或所有比赛的性能保证。全缓存仍会重新读取约 1GB/路媒体核验摘要，说明缓存复用已有效，仍有可优化的 I/O 成本。

当前本机 analysis_pipeline 约 3397 行，VideoAnalysisCard 约 2040 行，analysisClient 约 2089 行。行数本身不是缺陷，但身份、展示、产物与流程混在长文件中，会增加改动的连带风险。建议随模块迁移逐步收敛，而非立刻重写整个系统；每次迁移一个能力并保留旧新对照。

历史文档中的“没有 CI”“全站没有鉴权”“默认失败会伪造 demo 成功”等问题，已不能直接沿用。现有本机代码具备 token 边界、显式 demo 开关和页面懒加载，线上 CI 也已通过。与此同时，排除/跳过私有素材测试意味着还需要独立的真实场景验收作业，不能只依赖普通 CI。

本机 Windows 改动尚未提交，且落后线上 17 个提交。建议先保存适配改动为独立分支/提交，审查重叠修改与新依赖锁，再合并新版，避免环境与代码再次分叉。

## 创新性：系统整合有价值，科研贡献需要集中验证

YOLO 检测、RTMPose 姿态、单应性投影与常规多目标跟踪已有成熟研究。采用它们完成系统有工程价值，但不能单独构成原创算法贡献。[RTMPose 原论文](https://arxiv.org/abs/2303.07399)、[ByteTrack 原论文](https://arxiv.org/abs/2110.06864) 可作为已有方法与比较基线的起点。

市场上也已有匹克球录像分析、热力图、回合剪辑与击球统计产品。PB Vision 的官方材料介绍站位/击球可视化，SwingVision 介绍匹克球专项击球检测和自动集锦。因此，仅以“AI 分析匹克球”定位，差异化不够。这里引用的是厂商公开功能说明，未独立验证其准确率，也未对其未公开算法作判断。[PB Vision](https://help.pb.vision/en/help/articles/9831649-pickleball-ratings-ultimate-guide)、[SwingVision](https://swing.vision/newsletters/dinks-drops-live-line-calls)。

更有价值的主攻方向是“固定双摄条件下，结合球场几何与人工名册约束的四人身份持续跟踪”。它贴合当前最难的问题，也能形成明确实验：相同检测器与数据下，比较单摄跟踪、双摄、加几何约束、加冻结名册、加恢复机制。用身份质量和下游指标误差证明各部分贡献。

另一个可选方向是可追溯的人机协同复盘：每条建议都能定位视频证据，教练的接受、驳回和修正回流成标签，再验证是否降低人工复盘成本。可追溯架构本身不是独有创新，体育专项方法、数据集和用户收益才可能形成差异。

建议主攻一条研究线，把另一条作为产品验证路径，避免同时承诺动作识别、球拍融合、自动判罚和赛事管理全部领先。

## 产品与交付应验证的事情

一份有用的教练报告应回答：发生了什么、依据哪段录像、结论有多确定、下一次练什么、如何复测。建议先只做三类能可靠计算的结论，例如回合后到位时间、搭档间距变化、特定区域覆盖；具体指标及有效阈值需与教练共同定义，不能把移动更多简单解释为表现更好。

试点时记录首次成功分析耗时、用户必须操作的步骤数、需人工协助的比例、完整任务成功率、处理耗时/视频时长、显存峰值、人工纠错时间和教练重复使用情况。视觉效果与功能数量不能替代这些指标。

本地优先与模型失败显式展示是优势。进一步交付需要把拍摄告知/授权、访问范围、视频保留期限、导出删除、模型与数据使用条件列为清单。当前单机 token 方案有明确用途；多用户或远程访问应独立设计账号、权限和部署方式。

## 改进优先级与验收方式

| 顺序 | 具体动作 | 验收产
物 |
| --- | --- | --- |
| P0：统一基线 | 独立保存 Windows 适配，合并线上新架构/依赖修复，核对已实现与 planned | 可从干净环境重建；本机、线上版本与模型摘要对应 |
| P0：建立真值集 | 从多个拍摄日、场地与遮挡条件选 10–20 段视频作为首轮诊断集；按场次/拍摄日隔离测试集 | 人工身份、回合、几何/球位置标签；样本清单及使用范围。该规模只是起点，不保证统计充分性 |
| P0：四人身份 | 补完现有变更的短窗口、长缺口、换边、末段验收 | 每人覆盖率/缺口、IDF1/HOTA/交换数，视频证据与失败原因；不降低阈值掩盖错误 |
| P0：结果可信表达 | 按指标判断证据是否充分，区分观测与推断，绑定录像片段 | completed 但个人指标不可用时，页面明确解释与补救 |
| P1：指标测量验证 | 用人工复核/可测距离验证投影、速度、间距、回合边界 | 逐场误差分布、有效覆盖与置信范围；阈值与教练共同制定 |
| P1：教练闭环 | 只发布少量可靠建议，收集接受/修改/驳回及复测结果 | 相同录像下的人工复盘耗时对比，建议可用性和重复使用记录 |
| P1：性能与维护 | 分开统计准备、哈希、解码、推理、渲染；逐能力迁移模块架构 | 冷/热启动 P50/P95；对不可变源版本安全复用摘要；每次优化保留正确性对照 |
| P2：科研与规模化 | 在稳定基线上做消融、跨场地验证与小范围长期试点 | 公平基线、可复现实验包、用户收益与部署维护成本，再决定扩展功能 |

如果近期只能做三件事：统一本机与线上基线；建立有真值的四人身份验收集；让每条报告结论能追溯到真实视频证据。
