## Why

录制视频、事件标记和分析产物目前分散在默认磁盘目录中，长时间或双摄录制会持续占用系统盘空间，无法方便地使用移动硬盘。需要让用户在每次录制前通过本地应用的原生目录选择器临时选择存储根目录，并保证单摄和双摄的一次录制形成完整、可迁移的文件包。

## What Changes

- 在录制控制界面增加录制位置选择项，默认每次使用当前标准位置，不持久化用户上一次的自定义选择。
- 使用本地应用原生目录选择器选择电脑其他磁盘或移动硬盘目录。
- 为单摄和双摄统一建立按日期和 `capture_take_id` 区分的录制会话目录。
- 在会话目录中保存视频、分片、事件、标记、时间线快照、录制元数据和分析产物。
- 继续使用 SQLite 保存应用索引、查询关系和业务状态，不把 SQLite 拆分为每次录制一个数据库。
- 重新选择已有存储根目录时识别已有 `captures` 目录，避免创建 `captures/captures` 或覆盖历史录制。
- 在录制开始前校验目标目录可访问、可写且具备足够空间。
- 录制过程中发现目标存储中断或不可写时，立即停止相关录制，尽可能保存已完成内容，并将 CaptureTake 和源录制会话标记为失败。
- 删除、取消、恢复和分析任务使用会话目录中的实际路径，不再依赖固定默认目录。

## Capabilities

### New Capabilities

- `capture-storage-location`: 管理每次单摄或双摄录制的临时存储位置、会话目录结构、目录复用和存储故障处理。

### Modified Capabilities

- `recording-session-control`: 录制开始请求需要携带经过校验的存储位置，单摄和双摄会话必须记录最终会话目录，并在存储中断时进入失败终态。
- `analysis-artifacts`: 与录制会话关联的分析文件需要写入该会话的分析目录，同时保留 SQLite 和任务摘要作为应用索引。

## Impact

- 前端：`CaptureConsolePage`、`useCameraSetup`、`useCaptureRuntime`、录制类型和 API 客户端；新增目录选择器调用和录制位置状态。
- 后端：单摄 `session_service`、双摄 `sync_recording_service`、TrackRecorder/Coordinator、CaptureFinalizer、存储服务、分析任务和录制模型/Schema。
- API：单摄和双摄开始录制请求、会话响应、目录校验/选择桥接接口，以及错误状态和恢复响应。
- 数据库：录制会话或 CaptureTake 需要保存存储根目录/会话目录引用；现有 SQLite 作为索引继续保留。
- 运行环境：本地应用需要提供跨平台原生目录选择能力，并处理移动硬盘拔出、权限变化和剩余空间不足。
- 测试：覆盖单摄、双摄、重复选择已有目录、目录权限/空间错误、存储中断、取消清理和分析产物路径。
