## Context

当前双摄停止流程已经完成 TS 分段收尾，但随后在同一个请求中调用 `_register_session_videos()`，对 cam_1 和 cam_2 分别执行 TS 拼接、MP4 封装或重编码、解码校验和 Video 登记。该处理时间随录制长度增长，阻塞停止接口，也阻碍用户连续开始下一项录制。

现有任务管理页已经通过 `listSyncRecordings()` 展示双摄会话，并由 `SyncRecordingTaskCard` 渲染播放、工作台和分析入口。现有合并状态主要存在于进程内的 `get_merge_status()`，不适合作为任务列表的长期状态，因此需要把任务级状态落到会话持久化数据中。

## Goals / Non-Goals

**Goals:**

- 双摄停止请求在 TS 分段安全落盘后尽快返回。
- 每个双摄任务可以通过一个显式操作依次合并 A、B 两路。
- 任务列表能可靠显示待合并、合并中、已完成和失败状态。
- 合并前隐藏播放与分析入口；两路成功后恢复这些入口。
- 合并失败保留 TS，支持幂等重试，并防止同一任务并发合并。
- 保持单摄现有直接生成和登记 MP4 的行为不变。

**Non-Goals:**

- 不改变 TS 录制格式、分段策略、同步校准算法或原始文件内容。
- 不实现跨多个任务的自动合并队列；用户通过任务卡片逐个触发。
- 不改变取消录制时删除/清理半成品的语义。
- 不引入外部任务队列或新的基础设施依赖。

## Decisions

### 1. 按双摄任务触发一次合并

新增任务级合并操作。一次请求负责该任务的两路视频，后端在任务内部按 cam_1、cam_2 依次执行 Finalizer，避免用户分别操作两个机位，也避免两路同时占用过多 CPU/IO。

备选方案是前端分别提供 A/B 两个按钮；该方案会增加操作复杂度，并允许只完成一半而产生不清晰的任务状态，因此不采用。

### 2. 合并状态持久化在双摄会话记录中

在 `SyncRecordingSession` 的持久化 JSON 中记录任务级合并状态、错误信息及每路合并结果/Video ID。内存状态仅用于实时展示，不能作为唯一事实来源。任务列表读取会话时即可恢复状态，服务重启后也能识别失败或未完成任务。

备选方案是只依赖 `capture_finalizer` 的进程内状态；该方案无法支持历史任务列表和重启恢复，因此不采用。

### 3. 显式 API 启动后台合并

增加双摄任务合并 API。API 校验任务已停止且有可用 TS，立即返回“已提交/合并中”状态；后台执行两路 Finalizer，逐步更新会话持久化记录。重复点击在合并中返回当前状态，已完成时复用现有 Finalizer 的 manifest hash 幂等能力。

备选方案是让 API 同步等待 MP4 完成；这会重新把长耗时操作放回 HTTP 请求，不符合停止快速返回和批量录制的目标。

### 4. 任务级完成条件是两路都成功

只有 cam_1 和 cam_2 都有有效、已校验并登记的视频时，任务才标记为已完成，才能显示双路播放和 cam_1 分析入口。任一路失败都将任务标记为失败，同时保留已成功机位的结果与原始 TS，并允许重试失败或重新校验整项任务。

### 5. 停止阶段保留必要元数据，不做 MP4 后处理

停止流程继续完成 CaptureTake 终态化、分段关闭、会话 JSON 和 capture manifest 写入；与视频封装直接相关的 `_register_session_videos()` 从正常停止路径移出。需要避免停止阶段生成依赖 MP4 的 Video ID 或自动分析任务。

## Risks / Trade-offs

- [任务列表服务重启后遗留“合并中”状态] → 启动或查询时检查对应合并输出和临时文件；无法确认仍在运行时将状态恢复为失败/可重试，并保留 TS。
- [后台合并线程与删除任务并发] → 合并状态为 pending/running 时拒绝删除，或由删除 API 返回明确的冲突错误。
- [cam_1 成功、cam_2 失败造成部分产物] → 持久化每路结果；任务总体不标记完成，重试时复用已成功产物，不删除原始 TS。
- [旧历史任务没有新状态字段] → 读取缺失字段时根据 registered video IDs 和文件存在性兼容推导为待合并、部分完成或已完成。
- [用户在合并前误以为任务可分析] → 前端仅在任务级合并完成且有有效 Video ID 时显示播放和分析操作，后端分析入口也校验视频可用性。
- [双摄停止返回更快但 MP4 尚未产生] → 任务卡片明确显示待合并状态，并提供单一任务级操作，不将其显示为视频已就绪。

## Migration Plan

1. 先增加兼容读取和合并状态字段，再调整停止流程，确保旧 JSON 能被正常加载。
2. 增加显式合并 API 与后台执行逻辑，复用现有 Finalizer 的校验、登记和幂等逻辑。
3. 更新任务列表状态和按钮，限制合并前的播放/分析入口。
4. 使用短录双摄验证：停止立即返回、TS 保留、两路合并、失败重试、服务重启后的状态恢复。
5. 回滚时恢复停止路径中的自动注册逻辑；已经保存的 TS 和已生成 MP4 不受影响。

## Open Questions

- 合并后台线程是否需要在进程关闭时等待当前任务，还是统一标记为失败并在下次手动重试？本变更默认采用后者。
