## Context

当前任务状态接口同时承载单摄和双摄分析，但两类任务没有使用同一套可执行的阶段定义。后端的 `JobStore` 以单摄稳定阶段列表初始化任务，并在合并阶段时把未知阶段追加到列表末尾；`joint_tracking_v2` 的执行器又单独发出 `multiview-joint` 进度。因此，运行中的返回结果可能出现“报告生成”仍在 `pending`、而“双摄协同跟踪”已经接近完成的情况，且总体进度仍按阶段数量平均估算。

双摄结果合成器已经有“素材与同步检查 / A 机位 / B 机位 / 融合 / 指标 / 报告”的聚合概念，但它只在终态或合成阶段重新构造阶段列表；运行时的 `stages` 仍来自单摄列表和执行器回调。`late_fusion_v1` 依赖两个 dedicated child，`joint_tracking_v2` 不创建 AnalysisJob child，而是由一个 Parent 内的 A/B `ViewRun` 驱动。这两种模式必须有不同的阶段图，不能由前端猜测或通过追加阶段临时拼接。

本 change 将阶段图、状态转换、总体进度和 A/B 子进度统一成一个后端可执行、API 可序列化、前端可直接渲染的状态机契约。它只调整任务状态的记录和展示，不改变 YOLO、RTMPose、跟踪、融合或报告算法。

## Goals / Non-Goals

**Goals:**

- 为 `single_view`、`late_fusion_v1`、`joint_tracking_v2` 提供稳定、可测试、按执行模式选择的顶层阶段图。
- 让阶段顺序和真实执行顺序一致，保证报告只能出现在分析、融合、指标和可视化之后。
- 约束阶段状态转换，使未来阶段保持 `pending`，同一时刻最多一个顶层阶段为 `active`，失败或取消可以明确终止任务。
- 让总体进度基于阶段权重和当前阶段实际进度聚合，保持单调递增，并能反映双摄 A/B 子进度。
- 让任务 API 成为阶段顺序和状态的唯一来源，前端只负责展示，不再维护另一份单摄固定顺序。
- 保持历史单摄和历史双摄任务可读取，并为旧数据提供兼容投影。

**Non-Goals:**

- 不重写视频读取、目标检测、姿态识别、轨迹跟踪、融合或报告生成算法。
- 不在本 change 中重做 Vidat 标注包管理或片段管理交互。
- 不引入新的队列、分布式调度器或持久化存储系统。
- 不强制重写已经完成的历史任务阶段数组；历史数据只在读取或展示时按兼容规则解析。

## Decisions

### 1. 阶段图按执行模式显式定义

阶段图在后端集中定义并保留顺序，不再通过“单摄基础列表 + 额外阶段追加”生成。

- `single_view` 继续使用现有单摄稳定阶段 ID 和顺序，避免历史单摄任务的显示发生变化。
- `late_fusion_v1` 使用：`multiview-input-check` → `multiview-view-a` → `multiview-view-b` → `multiview-fusion` → `multiview-metrics` → `multiview-visualization` → `multiview-report`。
- `joint_tracking_v2` 使用：`multiview-input-check` → `multiview-joint` → `multiview-metrics` → `multiview-visualization` → `multiview-report`。

其中 A/B 阶段是 Parent 对 child 或内部 `ViewRun` 的聚合阶段，`multiview-joint` 是协同跟踪阶段。阶段列表的顺序由图定义决定，未知阶段不得被静默追加到列表中。

### 2. 使用纯状态机校验阶段转换

新增一个与存储和执行器解耦的状态机/聚合模块，负责根据执行模式生成图、应用阶段事件和计算快照。`JobStore`、双摄 Coordinator、执行器回调和结果合成器都通过这个模块更新状态。

状态机接受阶段开始、进度更新、完成、跳过、失败和取消事件，并校验：

- 顶层阶段最多一个 `active`；
- 当前阶段之前的阶段只能是终态；
- 当前阶段之后的阶段只能是 `pending`；
- 阶段进度在 0 到 100 之间，阶段终态的进度一致；
- 报告阶段不能在前置分析和后处理阶段完成前开始；
- 非当前图中的阶段 ID 不得改变任务阶段列表。

这样可以把“真实执行事件”和“前端展示快照”分开，避免终态合成器重新构造出一套与运行时不同的列表。

### 3. 使用模式化权重计算总体进度

每个阶段图携带稳定的阶段权重，权重总和为 100。总体进度由已完成阶段权重、当前阶段权重乘以阶段进度百分比和必要的 A/B 子进度共同计算，不再使用阶段数量平均值。

权重以代码中的可测试常量或配置集中管理，具体数值可以随真实运行时长校准，但同一图版本内必须稳定。状态机保存或聚合后的总体进度不得回退；成功任务为 100，失败或取消任务保留最后一个合法进度，不得把未来 `pending` 阶段标成完成。

对于 `late_fusion_v1`，A/B 顶层阶段的进度从 dedicated child 摘要聚合；对于 `joint_tracking_v2`，A/B 进度从 Parent 内部的 `ViewRun` 聚合。Parent 的 `progress` 和 `stage` 始终表示顶层图，不把两个子进度重复计入总体进度。

### 4. API 返回规范化的运行快照

任务状态 API 返回按模式图排序的 `stages`，每个阶段至少包含现有的 `id`、`status`、`progress`、`label`，并在可用时提供阶段开始/结束时间、耗时或错误信息。`stage` 表示当前 active 阶段，失败时表示失败阶段，成功或取消时表示最后一个有意义的终态阶段。

`viewRuns` 只在确实有 A/B 子运行数据时返回非空内容；没有子运行的单摄任务不返回空对象来制造假进度。前端使用 API 返回顺序渲染阶段条，并根据 `viewRuns` 是否有内容决定是否显示 A/B 子进度。

### 5. 兼容历史数据而不改变算法

通过 `analysisKind` 和 `executionMode` 选择新图。历史单摄任务缺少新字段时继续按 `single_view` 解析；历史双摄任务若缺少执行模式，则使用既有聚合结果或安全的兼容图，并在读取时归一化，避免因缺字段失败。新状态机不要求迁移或删除旧阶段 ID，回滚时仍可读取已有任务快照。

### 6. 以端到端回归测试锁定契约

测试分为四层：状态机纯单元测试、`JobStore`/Coordinator 集成测试、任务状态 API 序列化测试、前端阶段条渲染测试。重点覆盖当前已观察到的 `multiview-joint=95` 但总体进度约为 30%、报告位于运行阶段之前、`joint_tracking_v2` 的 `viewRuns` 为空等回归场景。

## Risks / Trade-offs

- 阶段权重是运行时长的产品化估计，不等同于真实剩余时间。通过集中配置、单调规则和测试固定语义，允许后续校准而不改变 API 结构。
- child 或内部 `ViewRun` 的遥测可能短暂落后于真实执行。聚合器应保留最近合法快照，并在没有新数据时避免把进度回退或错误标记为完成。
- 已完成的旧双摄任务可能没有完整的模式化阶段数据。读取兼容投影会让新旧任务在细节上存在差异，但优先保证可读和不破坏历史结果。
- 阶段 ID 会被前端、日志和测试引用。保留现有单摄 ID，并为双摄阶段建立明确 ID，避免用中文 label 作为业务判断条件。
- 前端如果仍保留本地固定阶段数组，会重新产生顺序漂移。应删除运行时排序逻辑，并为缺失/异常 API 数据保留清晰的降级提示。

## Migration Plan

1. 先实现并测试模式化阶段图、状态转换和进度聚合模块。
2. 将 `JobStore`、双摄 Coordinator/Executor/Composer 和任务状态 API 切换到统一快照；新建任务立即使用新图。
3. 为历史任务增加只读兼容归一化，确认旧单摄任务和已完成任务页面可继续打开。
4. 更新前端阶段条和 A/B 子进度展示，使用 API 顺序并补充运行、失败、取消、完成状态测试。
5. 在真实视频分析和双摄两种模式下验证日志、API 快照与页面显示一致，再移除仅用于临时拼接阶段的代码路径。

## Open Questions

- 首版阶段权重是否按当前实际样本重新标定，还是先采用固定默认权重并在运行数据积累后调整？这不影响状态机和 API 结构，但会影响用户对剩余时间的直觉。
- 前端是否需要在顶层阶段条内展开 A/B 子阶段，还是只在当前双摄阶段旁显示两个子进度？本 change 先保证两种展示都能从 `viewRuns` 得到一致数据，具体视觉布局可在实现阶段确定。
