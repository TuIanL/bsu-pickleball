## Why

后端已通过 `modular_v1` 拆出球员检测、球检测和姿态分析，并支持局部窗口、依赖规划及结果复用，但 Web 创建入口仍要求走完整比赛分析配置，用户无法在页面选择这些独立能力。本次把已有模块运行能力接入上传、单摄录制和双摄录制入口，让用户按目标创建分析，并在原素材下查看对应结果。

## What Changes

- 创建页统一提供完整比赛分析、球员检测、球检测、姿态分析和自定义组合；默认保留完整比赛分析，专项模式由后端能力目录门控，仅开放已实现且可准备的能力。
- 专项配置提供视频片段、采样和目标选择，自动展示后端展开的依赖；不要求当前三个能力不消费的球场、球网标定或名册。现有新/旧流程选择只保留在完整比赛分析内。
- 接通来源/模型准备、计划预览、模块提交，区分准备、预览和执行状态；配置变化使旧预览失效，提交校验预览计划指纹，避免执行内容悄然变化。
- 以既有 CaptureTake 权威来源提供双摄准备上下文，包括机位、源视频、PTS 和同步快照；复用同步校验，不把前端状态摘要拼造成同步标定，不触发完整分析的回合切分或场景标定。
- 模块进度与结果使用中文目标和节点状态，区分用户目标、自动依赖、结果完整性与产物质量，保留取消、错误诊断和技术详情；本期不增加检测框/骨架播放器。
- 素材历史记录保留模块任务及模式，专项结果进入模块结果页并可返回原素材；模块完成不得替换完整比赛结果的默认版本或错误开放报告、球路入口。
- 增加三个入口、双摄同步、预览失效、重复提交、结果归属及 legacy 兼容的针对性验证。

## Capabilities

### New Capabilities

- `frontend-analysis-mode-creation`：统一模式选择、专项表单、准备/预览/提交生命周期，以及跨入口复用和依赖展示。

### Modified Capabilities

- `analysis-local-validation`：补齐 Web 所需的服务可用性、模型准备反馈、双摄权威上下文和预览指纹校验合同，保持现有 CLI/API 兼容。
- `frontend-architecture-boundaries`：创建后按 engine 分流到完整结果或模块结果，并保留 Library 来源与导航语义。
- `analysis-flow-navigation`：明确模块任务完成去向、完整结果默认版本与实时任务状态的分离规则。
- `library-item-workspace`：历史记录区分完整与专项任务，专项结果独立打开，不参与完整比赛结果默认版本选择。
- `analysis-task-management`：模块详情面向用户呈现目标、依赖、中文状态、完整性和产物质量，正确保留来源导航。

## Impact

主要涉及 `NewAnalysisPage`、`RecordingAnalyzePage`、`MultiViewAnalysisSetupPage`、`AnalysisJobPage`、`ModularAnalysisRunView`、Library 历史/版本投影，以及新增共用专项创建组件、状态管理、类型和 API 模块。后端仅补充模块 API 与提交校验、来源关联元数据，复用 Registry/Planner/JobStore/Worker；不迁移现有算法、不新增推理能力、不改变身份阈值，也不修改仍在进行的四人身份分析变更。

新增请求字段和 API 为兼容性扩展，历史 engine 缺省仍为 `legacy_v1`，既有 CLI 和完整分析请求保持可用。无需增加前端依赖或引入新的工作流引擎。
