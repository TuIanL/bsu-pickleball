## Context

当前 Field Session 是球场采集任务的顶层容器，已经保存任务类型、比赛形式和摄像头方案；双摄录制由 FFmpeg 独立拉流并保存原始 TS 分段，普通预览则由每个 HTTP 请求独立打开 `VideoCapture` 输出 MJPEG。录制结束后，系统通过既有录制-分析桥接进入视频合并、标定和完整分析报告流程。

现场展示需要在同一场双摄录制进行时，把两路画面实时显示到另一块屏幕，并叠加轻量人体框。实时推理不能改变原始录制的时间轴、编码和终态化，也不能让展示模型失败阻断体验者的录像保存。当前完整分析包含姿态、球路后处理、可视化和报告生成，不能直接作为实时环路使用。

### 运行角色

- **操作屏**：配置摄像头、启动/停止采集、查看录制和展示旁路状态。
- **展示屏**：通过独立路由或展示 URL 订阅两路带叠加预览流，只消费实时展示数据，不控制录制。
- **原始录制链路**：继续由现有双摄 FFmpeg 进程负责，产物是后续正式分析的权威输入。
- **实时展示旁路**：在展示模式下按机位读取帧、执行轻量推理并输出临时 MJPEG 流；旁路产物不是正式分析 artifact。

## Goals / Non-Goals

**Goals:**

- 在 Field Session 层持久化 `display_mode`，默认 `standard`，支持显式 `showcase`。
- 展示模式仅允许双摄方案，并在任务详情、录制会话和展示状态中可追溯。
- 双摄录制开始后，为 cam_1 和 cam_2 提供低延迟的带人体框、track ID 和置信度的实时预览。
- 使用有界的最新帧策略，优先保持展示延迟，不因推理积压无限增加延迟。
- 在球检测模型和运行资源可用时叠加单视角球点与最近一段短轨迹；不可用时展示明确的 unavailable/degraded 状态。
- 实时展示旁路发生错误时，保留原始双摄录制，并允许前端回退到普通预览。
- 停止录制时安全停止展示旁路，随后不改变现有合并、分析任务创建和报告流程。
- 为标准模式提供默认兼容：历史 Field Session 和未选择展示模式的新任务不加载实时推理、不新增预览流。

**Non-Goals:**

- 不在实时旁路中运行 RTMPose 或完整姿态骨架推理。
- 不在本变更中实现实时双摄融合球路、弹跳识别、回合切分或战术语义。
- 不修改 FFmpeg 原始录制命令、TS 分段、CaptureTake 终态化或双摄合并规则。
- 不把实时叠加帧写入正式分析 artifact，也不让展示结果覆盖正式分析结果。
- 不把 `showcase` 加入既有 `capture_mode` 的 practice/match/engineering 业务枚举；展示模式是正交的显示运行配置。
- 不保证球点在所有场景下可用；球轨迹只在经过模型和现场性能验证后启用。

## Decisions

### 1. 在 Field Session 增加正交的 display_mode

新增 `display_mode: standard | showcase`，默认值为 `standard`。不扩展既有 `capture_mode`，因为 `capture_mode` 表示练习、比赛或工程任务，而 `display_mode` 表示是否启用现场实时视觉展示。后端在 `showcase + single` 组合下拒绝创建或启动，避免运行时出现只有一路画面的半配置状态。

历史数据库记录通过迁移获得 `standard` 默认值；更新接口允许在任务未进入 `live` 前修改，进入 `live` 后锁定本次任务配置。

### 2. 原始录制与展示旁路严格隔离

双摄 FFmpeg 录制仍然是权威录制链路。展示旁路在录制成功启动后单独启动，停止时单独回收。旁路异常只更新展示状态和错误原因，不终止 FFmpeg 进程、不修改 CaptureTake 状态、不删除已写入的 TS 分段。

旁路启动时将 `display_mode`、Field Session id、CaptureTake id、cam_1/cam_2 camera identity 和模型配置快照写入展示运行状态，避免前端修改任务配置后影响已运行的展示会话。

### 3. 为展示流使用任务级 ShowcaseRuntime

新增 `ShowcaseRuntime`/等价服务作为实时展示旁路的生命周期所有者。每个展示会话为两个机位维护独立的 reader/worker 和 bounded latest-frame queue：读取线程持续取帧，推理线程只消费最新可用帧，旧帧可丢弃。这样网络或 YOLO 推理变慢时画面会降低有效处理帧率，但不会把延迟越积越高。

展示流继续使用浏览器原生支持的 MJPEG，新增任务级展示流 URL；展示屏不直接访问 RTSP。状态信息通过现有 REST JSON 轮询或等价轻量接口获取，包含每个机位的连接状态、最近帧时间、推理 FPS、跟踪数量、球检测状态和降级原因。

### 4. 复用现有轻量视觉组件，但限制实时职责

人体路径复用 YOLO person detector、`MultiObjectTracker`、脚点估计和可选投影；实时预览优先输出 image-space bbox/track，投影和小地图属于可选增强，不作为展示流可用的前置条件。实时路径不调用完整 `AnalysisPipeline.run()`，不生成报告，不运行 RTMPose。

球路径复用球检测 adapter 和 `BallTracker` 的在线更新接口，只输出当前视角的球点和固定长度短轨迹。轨迹清洗、弹跳事件、球路重建和双摄融合仍由录制后的正式分析执行。

### 5. 分辨率与推理节奏采用可配置上限

展示旁路默认以较低处理分辨率和有限推理 FPS 工作，目标是双路合计可持续运行而非追求源视频帧率。每个机位的实际推理 FPS、输出 FPS 和最近更新时间必须回显，不能把目标配置伪装成实测性能。具体默认值应在目标比赛电脑和真实摄像头上压测后确定。

### 6. 普通预览保持原协议

现有 `/api/cameras/{camera_id}/preview` 继续输出不带分析的普通预览，供录制前设备确认和标准模式使用。展示模式使用独立的、带 session 约束的展示流 URL，避免普通预览客户端意外消耗模型资源，也避免展示屏在任务停止后继续读取摄像头。

### 7. 展示屏与操作屏分离

展示屏使用独立的全屏页面/路由，按 cam_1、cam_2 展示带叠加画面和简洁状态；操作屏保留现有 CaptureConsole 控件。展示屏断开不影响录制和展示 worker，操作屏关闭也不能自动结束 Field Session，只有明确停止录制才结束旁路。

## Risks / Trade-offs

- [Risk] 双摄各自运行 YOLO 可能超过比赛电脑的实时处理能力。→ 使用低分辨率、受控推理 FPS、最新帧丢弃和实测性能状态；必要时只保留人体框并关闭球检测。
- [Risk] 当前普通预览和 FFmpeg 录制已经分别打开摄像头流，展示旁路可能增加 RTSP 连接数。→ 展示流内部按机位复用单个 reader；在真实摄像头上验证并发连接上限，旁路无法启动时回退普通预览但不停止录制。
- [Risk] 球检测在高速、小目标和遮挡场景中不稳定。→ 球点/短轨迹是可选能力，必须带状态和置信度；不得用预测轨迹伪装成已观测球路。
- [Risk] 展示旁路与录制时间轴不同步。→ 实时叠加只作为即时反馈；原始 TS 和录制后正式分析仍是权威时间轴，展示状态记录最近帧时间和延迟估计。
- [Risk] 旁路线程、摄像头句柄或模型资源泄漏。→ 每个 reader、worker、queue 和 subscriber 都实现显式停止、超时回收和客户端断开清理，并增加重复启动/异常停止测试。
- [Risk] 数据库迁移影响历史 Field Session。→ 新字段使用 `standard` 默认值，读取历史缺失字段时以后端兼容默认处理，并补充迁移回归测试。
- [Risk] 展示屏误显示旧任务画面。→ 展示流 URL 绑定 ShowcaseRuntime id 和 CaptureTake id，停止后立即失效，前端切换任务时清空旧订阅。

## Migration Plan

1. 增加 Field Session `display_mode` 数据库字段、schema 字段和默认值；先部署后端兼容读取，再接入前端选择器。
2. 在标准模式下验证完整回归，确认不加载 ShowcaseRuntime、不改变普通预览和双摄录制。
3. 增加 ShowcaseRuntime、带叠加 MJPEG 流和状态接口，先使用虚拟摄像头/固定视频做生命周期测试。
4. 将展示旁路接入双摄录制开始、停止、取消、异常恢复和页面重载流程。
5. 接入独立展示屏和展示模式配置，验证录制文件、CaptureTake 状态和结束后的完整分析均与标准路径一致。
6. 在目标比赛电脑和真实双摄上进行至少连续 10 分钟稳定性、断流恢复、模型降级、停止收尾和报告生成验收。

回滚时将新任务默认恢复为 `standard`，关闭展示模式入口；既有双摄录制、普通预览和录制后分析不需要回滚。展示旁路产生的临时状态和缓存可以清理，但不得删除原始录制或正式分析产物。

## Open Questions

- 目标比赛电脑的 CPU/GPU 型号、可接受的双路预览 FPS 和端到端最大延迟是多少？
- 展示模式是否要求每一路画面都叠加球点，还是允许只在参考机位展示球点？
- 现场是否已经有可靠的球检测权重和足够的训练/验证视频，能否在比赛前决定默认关闭球轨迹？
- 展示屏是与操作屏同一前端实例的新路由，还是需要单独启动一个浏览器窗口/展示 URL？
