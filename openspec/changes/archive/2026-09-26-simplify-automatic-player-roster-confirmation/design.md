## Context

现有 `GET /api/analysis/players/bootstrap` 优先读取历史任务，否则只对源视频前 3 秒做稀疏人体检测。新视频预检按出现次数和检测置信度选人，尚未排除目标球场外的人；候选 `anchor_bbox` 是各人首次出现的框，`reference_timestamp_ms` 却取检测人数最多的时刻。前端因此常要重新截帧、逐人画框。已有衣着特征、目标球场球员筛选、双机位关联与质量诊断模块，但预检未把这些证据整合起来。

分析任务创建时会冻结名册；正式追踪完成后才产出 `bootstrap_binding_audit`。当前审计在缺少球场坐标时无法确认绑定，在有坐标时又会按同一编号的全片位置做宽松比较，尚不足以证明中段画面上的人就是正式轨迹中的该人。改造必须同时处理预检、确认交互和正式身份消费。

## Goals / Non-Goals

**Goals:**

- 自动优先展示四名目标球场球员的 P1–P4 卡片及可核对的参考画面；正常情况不要求用户寻找帧或逐人画框。
- 每张卡片的图、bbox、时间和机位对应同一次实际观测；远景以完整人物和球衣为主要证据。
- 用户可以纠正候选与 P 槽位的映射；经确认的映射须在正式分析中按实测观测核验，失败不得冒充成功。
- 保持单摄、双摄、候选不足、模型不可用与跳过名册等路径可用；普通分析不因预检失败而中断。

**Non-Goals:**

- 本次不加入球员姓名输入、跨比赛球员档案或人脸识别。
- 不要求仅凭一帧自动确定真实姓名、正式 Team A/B 或录制开始时的端位。
- 不对完整比赛运行第二套正式分析 Pipeline，也不为了凑足四人接纳邻场球员或观众。

## Decisions

### 1. 受限多窗口预检，确定性选帧

以所选分析片段为时间范围，在中段优先抽取若干短窗口，必要时向前后扩展；每窗口运行有预算上限的人体检测和短时关联。复用目标球场选择、球场投影与衣着特征的既有实现；仅在已有同步和标定证据可用时融合 B 机位。候选评分综合目标球场成员概率、跨帧持续性、四人覆盖、遮挡/模糊/裁剪质量、外观区分度与双摄一致性。四个框或候选轨迹无法可靠区分时返回不足或不确定，不以“检测到四个人”为成功条件。

选择一张四人同时清晰的主参考帧；若某人的最佳图像来自附近的另一帧，其卡片使用那次观测并显示时间和机位。主参考帧只叠加该帧实际存在的框，绝不将其他时刻的 bbox 画在其上。相同视频版本、片段范围、同步/标定版本和模型配置产生可缓存的同一预检结果，避免页面重开时 P 建议顺序随机变化。

取舍：随机中间帧实现简单，但中场休息、换边、遮挡和邻场运动仍会误选；限定时间和帧数预算的多窗口方案能改善可靠性，同时维持预检与完整 Pipeline 的边界。

### 2. 候选身份与用户 P 槽位分离

候选使用预检运行内稳定的 `candidate_id`；P1–P4 是用户确认的展示槽位，不能以检测顺序或既有任务的 `Player_N` 字符串直接宣称正式身份。新响应采用版本化契约，包含每候选的来源视频/机位、时间、bbox、裁剪图来源、球场位置、证据质量及主参考帧的独立元数据。现有 v1 客户端在过渡期仍可读取旧响应；新版确认页消费新契约。画面资源由现有受控视频取帧接口扩展或组合生成，避免把大块 base64 图像塞进 API JSON。

选中的 `candidate_id → P 槽位`、锚点与版本信息在创建 Job 时随名册冻结。自动候选也必须填写 `source_view_id`；手工框选和自动候选使用同一锚点契约。`display_name` 字段保留，第一阶段不作为必填项，也不由系统把 P 编号伪装成姓名。

取舍：沿用 `canonical_player_id` 作为预检候选 ID 可少改类型，但会继续混淆预检身份、用户 P 标签和正式追踪 ID，因此采用显式区分。

### 3. 确认页以四张卡片为主

加载后直接显示四张带 P 编号的人物卡片和带编号的主参考画面。用户可交换卡片对应的 P 槽位，或在参考画面点击其他已检测人物进行替换；只有自动证据不足或纠正失败时才展开视频选帧及手工画框。候选不足四人时保留已可靠确认的人，不补假候选，并明确指出缺少哪个槽位。

身份确认后再以简短区域请求人工核对 Team A/B 和初始端位，保持现有依赖队伍身份的指标语义。跳过时继续普通分析，并对依赖正式身份的指标给出不可用原因。双打四槽、单打两槽共用同一交互模型。

### 4. 正式绑定按同时刻证据建立唯一映射

正式分析产生逐帧观测后，在锚点时间附近、对应机位比较确认 bbox 与正式轨迹观测；有标定时加入球场坐标，衣着描述子与另一机位观测作为辅助证据。以一对一匹配建立 `P 槽位 → formal canonical player` 映射，记录时差、几何/外观分数、证据来源和冲突原因；无唯一可信匹配则该槽位 `confirmed=false`。仅凭相同 `Player_N` 字符串、全片任意时刻的位置相近或单一低质量衣着特征不得确认。

正式轨迹 ID 本身不静默改号。叠加画面、报告和依赖 Team A/B 的计算以通过审计的映射解析用户 P 标签；未通过的槽位保留诊断并降级关联指标。这样中段选择的清晰画面可成为身份锚点，又不要求从中段倒推比赛开始时的轨迹编号。

Job 创建时冻结的名册和回合上下文仍记录用户确认的 P 与 Team 语义；分析完成后的映射是独立、可审计的解析层，不回写或改动这些不可变快照。生成依赖正式轨迹的指标时才以该映射查找球员；映射未确认就保持不可用。

取舍：在完整追踪开始前强行用中段框初始化 P 编号需要回溯或第二遍追踪；后验唯一映射复用现有 Pipeline，且可审计。

## Risks / Trade-offs

- **标定或模型不可用** → 不据此硬补四人；展示可用候选、具体原因和手工入口，允许跳过。
- **双摄时间未准确同步** → 只用可信的同步映射融合证据；否则各机位独立呈现，不做跨机位身份断言。
- **相同球衣、遮挡和换边导致匹配歧义** → 使用时空、球场、外观多证据与唯一性门槛；失败为 `partial`/`unavailable`，不自动换号。
- **多窗口预检增加页面等待时间** → 限定抽帧预算、缓存结果并显示进行中状态；复用已通过质量检查的旧产物时仍需校验图框时间和来源。
- **既有消费者直接使用正式 `Player_N`** → 分阶段接入绑定映射，逐一覆盖队伍指标、叠加画面与报告；加入未绑定时不显示错误 P/姓名的回归测试。

## Migration Plan

1. 增加版本化候选响应与受限多窗口预检，保留旧响应路径；先用真实素材核验候选质量与耗时。
2. 切换确认页为四卡片交互，并使自动/人工锚点按统一契约冻结；旧名册快照仍可读取。
3. 升级绑定审计和 P 到正式身份映射消费；仅新契约使用强绑定语义，旧快照按原有能力展示并标明证据等级。
4. 验证单/双摄、单/双打、片段分析及跳过路径后再移除旧 UI 默认流程。回滚可切回旧确认页与 v1 响应，不删除既有名册数据。

## Open Questions

- 实施时需量测真实素材上的检测耗时与目标球场误选率，以确定抽帧预算及缓存失效策略；预算不足时优先返回诚实的部分候选。
- 需确认所有正式轨迹与预检帧的时间基准和片段起点换算，再确定同时刻匹配容差。该校验是启用自动确认的前置任务。
