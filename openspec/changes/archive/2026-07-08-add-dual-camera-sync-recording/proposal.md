## Why

当前现场采集只能围绕单个摄像头开始和停止录制，无法满足双摄像头必须同步启动、同步停止、异常时同步重启的采集要求。已有独立 Python 同步录制脚本已经验证了可用的 FFmpeg 编排思路，现在需要把它沉入项目的采集工作流，避免现场录制依赖人工同时操作多个窗口。

## What Changes

- 新增双摄同步录制能力：一次录制会话同时管理两路摄像头，开始、停止、异常中断和分段重启由后端统一协调。
- 将现有独立 RTSP 同步录制脚本的核心逻辑移植为后端服务，复用已有摄像头注册、探测和 Field Session 上下文。
- 在采集控制台中，当 Field Session 使用 `dual` 摄像头方案时，提供两路机位选择、连接探测、短录测试、同步开始/停止和分段状态展示。
- 双摄录制完成后，将主机位视频接入现有“创建分析任务”流程，副机位视频作为关联素材保留，避免阻塞当前单视频分析管线。
- 保留单摄录制路径的现有 API 和 UI 行为，不引入 breaking change。

## Capabilities

### New Capabilities
- `dual-camera-sync-recording`: 定义双摄同步录制会话、同步启动/停止、同步分段重启、短录测试、输出文件登记和状态展示。

### Modified Capabilities
- `capture-workflow`: 采集控制台在双摄方案下需要展示双机位准备区、同步录制控制和双摄录制完成面板。
- `device-drawer`: 设备抽屉需要支持为不同机位槽位选择摄像头，而不是只设置单个当前摄像头。
- `recording-session-control`: 录制控制需要支持双摄同步录制入口，并保持单摄录制入口兼容。

## Impact

- 后端：新增同步录制服务和 API 路由，扩展录制模型以表达双摄会话、机位、分段和关联文件。
- 前端：扩展 `CaptureConsolePage` 的设备选择、预览、测试和录制状态 UI；扩展 `analysisClient` 与类型定义。
- 存储：新增双摄录制会话 metadata、两路 `.ts` 分段文件、首尾帧测试产物和主机位视频登记信息。
- 依赖：继续依赖系统 FFmpeg；可复用 OpenCV 提取首尾帧，不新增必须的前端依赖。
- 测试：新增后端同步录制服务单元测试、API 测试和前端双摄控制台交互测试。
