## Context

实时录制实施页 `CaptureConsolePage` 已经接入 `useCaptureRuntime`、`useCameraSetup` 和 `useLiveCoding`，能够完成单摄/双摄录制、事件编码、比分和时间线同步。当前页面的主要问题是布局仍以紧凑调试控制为中心，录制控制、运行指标和系统健康信息分散在不同区域。

后端已经持久化 `CaptureTake`、`CaptureTrack` 和 `MediaFragment`，录制会话也保存 `storage_root`、`session_dir`、目标 `fps`、分辨率和状态。现有接口没有面向工作台的统一运行状态快照，存储容量、当前文件大小、平均码率和轨道健康状态无法由前端可靠拼装。

本设计必须兼容当前未提交的录制工作台改动，不回退既有的双摄同步、CaptureTake 统一时间线和恢复逻辑。

## Goals / Non-Goals

**Goals:**

- 让实时录制实施页在桌面端采用目标工作台的信息层级：标题栏、双机位预览、录制控制条、事件时间线、三栏底部信息区。
- 新增按 `capture_take_id` 查询的运行状态快照 API，统一提供存储、媒体、轨道、同步和错误状态。
- 复用现有录制数据源和文件归档，不改变录制控制命令、事件语义或分析流程。
- 明确区分目标配置、实时测量、采集中和不可用指标。
- 让页面在 API 暂时不可用时保留录制主控制能力，并显示明确的状态降级。

**Non-Goals:**

- 不改录制任务列表、录制回放页或其他内部页面。
- 不做移动端专属布局；仅保证桌面端 1024px 以上可用。
- 不增加音频编码能力；当前录制链路为视频录制，系统状态不得显示虚构的音频状态。
- 不重新设计录制状态机、CaptureTake 数据模型、事件协议或时间线算法。
- 不引入 WebSocket、外部监控系统或新的数据库。

## Decisions

### D1: 运行状态使用 CaptureTake 级快照接口

新增 `GET /api/capture-takes/{capture_take_id}/runtime-status`，由后端聚合当前 Take 的源会话、轨道、分片、会话目录和文件系统信息。前端不分别拼接多个源接口来推断状态。

响应分为 `storage`、`recording`、`tracks`、`sync` 和 `updated_at` 五个区域。字段使用明确的状态联合：`ready`、`collecting`、`unavailable`、`error`，以便前端区分“暂时没有测量结果”和“系统故障”。

替代方案：前端并行轮询源录制接口、存储接口和分片接口。该方案会产生短暂不一致，且把路径、文件大小和状态聚合逻辑暴露到浏览器，因此不采用。

### D2: 后端计算文件大小和码率

后端使用 CaptureTake 会话目录内当前可见的分片文件大小作为当前文件大小来源，并以最近一次状态快照间隔计算平均写入码率；无法读取文件时返回 `error` 和原因。已完成分片和当前活动分片都必须纳入聚合，路径必须来自已校验的会话目录。

码率明确标注为后端测得的平均写入码率，不声称是编码器瞬时码率。有效帧率优先使用录制器/媒体诊断已有结果，没有可用测量值时返回 `collecting` 或 `unavailable`，不得回退为目标 fps 并标记为实测。

替代方案：前端用文件大小除以前端计时器计算码率。该方案受浏览器刷新、网络延迟和多轨道不同步影响，且无法表达文件读取失败，因此不采用。

### D3: 页面轮询与录制控制解耦

`CaptureConsolePage` 在 `recording`、`stopping`、`recovering` 阶段轮询运行状态，建议间隔为 2 秒，并以 `captureTakeId` 丢弃过期响应。停止、取消和事件编码继续走现有 hooks，不因运行状态轮询失败而阻塞主录制控制。

页面在运行状态接口失败时保留最后一次成功快照，同时显示“状态更新失败”和最后更新时间；从未成功获取时使用可识别的 loading/unavailable 状态。

替代方案：把运行状态轮询放入 `useCaptureRuntime`。这会扩大生命周期 hook 的职责并与现有 source-session 轮询耦合，因此运行状态作为页面层或独立 `useCaptureRuntimeStatus` hook 管理。

### D4: 视觉重排优先复用现有 capture 组件

复用 `CameraPreviewCard`、`EventActionToolbar`、`MiniTimeline`、`RecentEventsCard`、`RecordingControlPanel` 和现有 capture CSS tokens。`CaptureConsolePage` 负责构造 ViewModel 和回调，展示组件不直接访问 API 或 hooks。

页面布局按桌面端 CSS Grid 实现：双摄为两列预览，录制控制条为固定信息带，底部为“最近事件 / 系统状态 / 快捷操作”三列。1024px 视口下允许底部区域折为两列，但不产生横向滚动。

### D5: 系统状态只展示可验证信息

系统状态卡展示存储可用性、录制进程/轨道状态、同步状态和事件同步状态。音频编码、网络质量等没有后端证据的指标不展示；摄像头在线状态仅在后端状态快照或已有探测结果明确提供时展示。

### D6: API 向后兼容并支持降级

新接口为附加接口，不改变现有 start/stop/cancel 响应。旧录制或缺少分片诊断字段时，后端仍返回会话状态、目标配置和存储状态，其余指标标记为 `unavailable`。前端不得因为单项指标缺失而隐藏整个工作台。

## Risks / Trade-offs

- [活动文件在操作系统层面暂时不可读] → 后端将该指标标为 `collecting` 或 `error`，保留上一次快照并返回可读错误，不让前端伪造数值。
- [双摄两路状态更新时间不一致] → API 返回统一 `updated_at`，轨道状态单独列出；页面以 Take 状态作为主状态，以轨道状态解释局部异常。
- [频繁读取外部硬盘和目录造成 I/O 压力] → 运行状态接口限制轮询频率，后端只读取当前会话目录，必要时缓存短时间快照。
- [接口轮询与停止收尾同时发生] → 后端允许终态快照返回；前端以当前 phase 和 `captureTakeId` 校验响应，终态后停止轮询。
- [现有未提交改动与新布局存在冲突] → 实施前先基于当前工作区逐项核对组件和测试，不覆盖用户已有修改。

## Migration Plan

1. 先实现运行状态响应模型、聚合服务和 API 单元测试。
2. 增加前端类型、API client 和运行状态 hook，保持现有页面结构可编译。
3. 重排 `CaptureConsolePage`，接入真实指标并覆盖 loading、collecting、unavailable、error 和终态。
4. 在桌面端 1440×900、1280×800、1024×768 验证布局、轮询和录制控制回归。
5. 若新接口不可用，前端降级到已有会话信息，不影响录制开始、停止、取消和事件标注。

## Open Questions

- 运行状态接口的平均码率采样窗口是否固定为最近 2 秒，还是由后端根据最近两次快照动态计算？实施时默认使用最近两次成功快照。
- 有效帧率是否需要扩展 FFmpeg 进程实时 telemetry；若现有诊断只能在分片完成后提供，页面应显示“采集中”而非目标帧率。
