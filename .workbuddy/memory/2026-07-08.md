## 网络摄像头地址排查（环境/抓取设备）
- 用户通过网线接了一台网络摄像头（用于匹克球视频采集），忘记其 IP。
- 本机网络：`en0` = Wi-Fi 172.18.211.110/20（校园网，网关 172.18.208.1）；`en8` = 有线 192.168.1.200/24（网线直连摄像头所在网段）。
- 现象：连 Wi-Fi 时网线读不到摄像头；断开 Wi-Fi 后摄像头回应 ARP。
- 诊断：摄像头为 Wi-Fi+网口双模。有 Wi-Fi 时切无线、有线 PHY 休眠；断 Wi-Fi 才回落到有线出厂静态 IP（192.168.1.x）。校园 Wi-Fi 大概率有客户端隔离，即使走无线也跨客户端不可达。
- 验证手段（Wi-Fi 开着时均失败，符合预期）：ping 扫描 192.168.1.0/24 全 incomplete；ONVIF WS-Discovery 无响应；mDNS(_rtsp/_http) 无响应；172.18.208.0/20 内无摄像头类设备。
- 解法：关 Wi-Fi → 用 `find-camera.sh` 扫出摄像头 192.168.1.x IP → 进其 Web 管理页关闭/忘记 Wi-Fi（仅用有线）→ 重开 Wi-Fi。此后摄像头常驻 192.168.1.x，Mac 可同时看摄像头+上网。
- 产物：`find-camera.sh`（项目根，离线可用，ping 扫描 192.168.1.x 并自动开浏览器）。

## 录制跳帧故障排查与修复
- 问题：录制功能能正常录，但回放时每隔几秒卡 1-2 秒（帧被跳过），实时预览正常。
- 根因：`backend/app/camera/recorder.py` 中 FFmpeg 命令行参数冲突——`-c:v copy`（流复制模式）与 `-r`、`-s`、`-fps_mode cfr` 不可同时使用。复制模式下这些参数不生效，反而导致 FFmpeg 通过篡改 PTS 时间戳来"凑"帧率，输出 MP4 时间轴不规则，浏览器播放时卡顿。
- 预览不受影响：预览走独立的 `cv2.VideoCapture` 路径，与 FFmpeg 无关。
- 修复：
  - 从 `recorder.py` 的 FFmpeg 命令中移除 `-r`、`-s`、`-fps_mode cfr`，仅保留 `-c:v copy` + `-c:a aac`，让 FFmpeg 原样复制源流。
  - 清理 `Recorder.start()` 方法签名，移除已无实际效用的 `fps` 和 `resolution` 参数。
  - 同步清理 `session_service.py` 调用处，不再传 `fps` 和 `resolution`（它们作为 request/session 元数据字段保留）。
- 二次排查发现修复后仍然卡顿：分析 `rec_20260708_012732.mp4` 帧 PTS，发现 4.022s-7.989s 存在 3.97s 大缺口（361 帧丢失）。
- 根因升级：预览模块（`preview_service.py`）用独立 `cv2.VideoCapture` 连接摄像头，加上 FFmpeg 录制连接，共 2 路并发 RTSP → 摄像头 RTSP 服务过载丢帧。
- 修复：前端 `App.tsx` 中 `handleStartRecording` 录制前自动断开预览（`setPreviewStatus("idle")` + key 递增），`handleStopRecording`/`handleCancelRecording` 停止后自动恢复预览。录制期间 UI 显示"录制期间预览已暂停"提示。

## 录制视频慢动作回放修复
- 问题描述：摄像头录制视频回放时感觉慢动作（零点几倍速）
- 诊断：ffprobe 检查 `rec_20260708_022528.mp4` 发现文件元数据完全正常（311 帧 / 10.367s = 30fps，PTS 间隔稳定 33.33ms），但用户主观感受慢动作
- 根因：FFmpeg 录制命令中 `-use_wallclock_as_timestamps 1` + `-fflags +genpts` + `-vf fps=30` 三重时间戳操作叠加。`fps=30` filter 基于 Unix 时间戳（1751940000.x）做帧率转换存在已知精度问题，导致输出帧数和实际画面时长不对齐
- 修复：完全移除时间戳覆盖和 `-vf fps` filter，改用 `-r 30 -vsync cfr` 输出选项。`-r` 作为输出选项直接控制编码器输出帧率，`-vsync cfr` 启用恒定帧率模式（自动补帧/丢帧），比 filter 链更简洁可靠
- 移除的 flag：`-fflags +genpts`、`-use_wallclock_as_timestamps 1`、`-vf fps=X,scale=...,format=yuv420p`、`-avoid_negative_ts make_zero`
- 新增的 flag：`-r 30`、`-vsync cfr`、`-pix_fmt yuv420p`、resize 改为 `-s WxH`

## 单摄 90fps 周期性卡顿诊断（仅检查，未改代码）
- 文件：`backend/data/recordings/2026-07-08/test/rec_20260708_091215.mp4`（196s / 17640 帧 / 标称 90fps）
- 分析结论（帧内容比对，非 PTS——PTS 是均匀的 1/90，掩盖了卡顿）：
  - 检测到 55 处「相同帧连续重复」冻结段，最长 2.43s，平均 1.19s，平均间隔 2.36s。
  - **冻结帧占整段录制的 33.5%（5902/17640 帧是静止重复的）**——与用户「每 2-3 秒卡 1 秒」完全吻合。
  - 机制：摄像头在 90fps 下无法持续稳定供流 → 周期性欠载，驱动返回上一帧缓冲或重复帧，录制循环盲写导致长段重复帧。
- 关键反证（用户自述）：**摄像头自带系统软件在 90fps 同样卡，降到 60fps 即流畅** → 排除本项目 Web/后端代码责任，判定为硬件/接口带宽瓶颈（USB 带宽 or 未压缩格式 YUY2/NV12 在 90fps 超限）。
- 后续可选项（待用户决定，本次未实施）：
  1. 让摄像头输出 MJPEG 压缩流（OpenCV 开流前 `CAP_PROP_FOURCC=MJPG`）再设 90fps——最有可能保住 90fps。
  2. 直连主板 USB3 口、短线、不用集线器；或 90fps 下降分辨率（如 1280x720）。
  3. 直接用 60fps（已验证稳定）。
  4. 软件侧加「重复帧丢弃」避免下游分析看到冻结段（仅掩盖，真实运动在冻结期仍丢失）。
